# リサーチ: Enable tests on all branches

**ステータス**: 完了
**日付**: 2026-02-15

## 概要

`deploy.yml` の変更に関する技術的アプローチの調査結果。

## 決定事項 (Decisions)

### 1. `deploy.yml` の変更による対応

**決定**: 既存の `.github/workflows/deploy.yml` を修正し、トリガー条件とジョブ依存関係を調整する。

**根拠**:
- プロジェクトの構成が単一のワークフローファイルであり、管理が容易。
- GitHub Actions の `if` 条件式を用いることで、ジョブレベルでの実行制御が容易に実装可能。
- `build` ジョブと `deploy` ジョブの関係（`needs: build`）を維持しつつ、ブランチ条件を追加するだけで要件を満たせる。

**詳細**:
- トリガー: `on: push` の `branches` リストから `master` 制限を削除し、全ブランチ対象とする。
- Buildジョブ: 条件なし（常に実行）
- Deployジョブ: `if: github.ref == 'refs/heads/master'` を追加し、masterブランチ以外ではスキップされるようにする。

### 2. トリガー設定

**決定**: `on: push` 配下の `branches` 指定を `['**']` (全ブランチ) にするか、リストを削除してデフォルト（全ブランチ）にする。

**根拠**:
- 仕様「すべてのブランチへの push イベント」を満たすため。

## 検討した代替案 (Alternatives Considered)

### A. ワークフローの分割 (`ci.yml` と `deploy.yml`)

- **提案**: テスト専用のワークフローと、デプロイ専用のワークフローに分ける。
- **却下理由**:
  - `deploy` ワークフローが `ci` ワークフローの完了を待つ設定（`workflow_run` トリガーなど）が必要になり、設定が複雑化する。
  - 現状の構成（`needs: build`）の方がシンプルで、ビルドアーティファクトの共有などが直感的に行える。
  - プロジェクト憲法「単純性と可読性」に反して複雑になる恐れがある。

### B. Pull Request トリガーの使用

- **提案**: `on: pull_request` を追加する。
- **備考**:
  - `push` トリガーですべてのブランチをカバーすれば、PR作成元のブランチへのプッシュでCIが走るため、重複実行を避けるために `push` のみとするのがプロジェクトの方針と合致する（既存も `push` ベース）。
  - 重複実行（PRとPush両方）を避けるため、今回は `push` 全てというシンプルな変更に留める。
